# AI engineering decisions

This document decides the AI layer. `07-ai-provider-layer.md` specifies the seam, the adapters and the routing; `04-item-generation.md` specifies the generation contract and the verification pipeline; `10-quality-and-evaluation.md` specifies the evals; `12-open-questions.md` holds what neither settled. This document chooses the numbers those three left open, and records where a live re-read of the provider documentation overturns a sentence in one of them.

Every number here carries the URL it was read from and one tag. `[verified]` means read directly off a primary source fetched on 2026-09-20. `[single-source]` means one source only. `[inferred]` means it follows from a decision rather than from a source. `[measured]` means computed in this repository on 2026-09-20 with the command recorded beside it. Every dollar figure in this document is emitted by `python3 tools/cost_model.py`, whose inputs are the price and token tables below with their tags, and `tests/tools/test_cost_model.py` fails when this document or `docs/operator/ai-operating-costs.md` prints a dollar figure the calculator does not emit. A figure with no line in that file does not belong here. Nothing is recalled from memory. Where a page does not print a figure, this document says unknown from the loaded page rather than supplying a plausible one, and the unsourced claims are collected at the end so the gaps stay visible.

Four quality floors are not tradeable against cost, and nothing below relaxes one. The verifier never sees the key. An unverified item is never served. The deterministic checks decide before a model does. A disagreement routes to review and is never averaged. No key material enters a log, a URL or an audit detail.

## What a live re-fetch changed

`07-ai-provider-layer.md` was written on 2026-09-19 and every figure in its adapter tables was re-fetched on 2026-09-20. Most held. Six facts the provider documentation prints today are absent from 07, and four of them change a cost figure or break a live code path.

**Temperature is a 400 on the models this project routes to, at any value.** "On Claude Fable 5.1, Claude Mythos 5.1, Claude Fable 5, Claude Mythos 5, Claude Mythos Preview, Claude Opus 5, Claude Opus 4.8, Claude Opus 4.7, and Claude Sonnet 5, non-default `temperature`, `top_p`, or `top_k` values return a 400 error on every request, regardless of whether thinking is used" (https://platform.claude.com/docs/en/build-with-claude/thinking [verified]). 07's routing table sets a temperature per role, tutor 0.3, generator 0.7, diagnostician 0.2, and grader, verifier and transcriber 0.0, and every one of those is a 400. `app/providers/anthropic.py` sent `"temperature": request.temperature` unconditionally with a default of 0.0 in `ProviderRequest`, so **every real call the application made would 400**. This was found by running a real call, not by reading, and `BUILD-LEDGER.md` records that the wire mapping had never executed against a live key. Fixed 2026-09-20: the field left `ProviderRequest` entirely rather than being made optional, because no routed model accepts it and an optional field is an invitation to send it again; `tests/providers/test_anthropic.py` asserts the wire body carries no `temperature` key. It also removes a design premise: 07 calls the three zeros "not tunables" because a grader that varies run to run makes the agreement check meaningless, and there is now no parameter that pins them.

**Thinking is on by default on the two models this project routes to most.** "On Claude Opus 5, Claude Sonnet 5, Claude Fable 5.1, Claude Mythos 5.1, Claude Fable 5, Claude Mythos 5, and Claude Mythos Preview, thinking is already on and needs no configuration" (same URL [verified]). Thinking tokens are billed as output and count toward `max_tokens` (https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost [verified]). 07's trap list records only that `thinking: {type: "enabled"}` returns 400 on Claude 4.7 and later, and `app/providers/anthropic.py` refuses the whole `thinking` key on that reading. Not sending a thinking parameter does not turn thinking off; it leaves the default on. Sonnet 5 accepts `thinking: {"type": "disabled"}`; Opus 5 accepts it at effort `high` or below and returns 400 at `xhigh` or `max` [verified].

**There is an effort parameter, and its default is the expensive end.** `output_config.effort` takes `low`, `medium`, `high`, `xhigh` and `max`; "By default, Claude uses high effort, spending as many tokens as needed for excellent results", and at `high` "Claude almost always thinks" (https://platform.claude.com/docs/en/build-with-claude/effort and https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost [verified]). Effort is supported on Opus 5 and Sonnet 5 and is not supported on Haiku 4.5 (effort page compatibility list [verified]).

How much thinking actually costs is `[inferred]`, and the only live anchor is weaker than an earlier draft of this document claimed. Anthropic's steering page runs a prompt-cache demonstration on Opus 5 with adaptive thinking over a 10,000-character text excerpt and reports `output_tokens` of 1033, 1630 and 1468 across three turns; the third of those runs at effort `medium` rather than the default, and the page prefaces the block with "you may see slightly different numbers" (https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost [verified]). It establishes the order of magnitude and nothing finer, and every thinking figure in the cost model rests on it.

**Token counting is free.** `POST /v1/messages/count_tokens` is "free to use", subject to its own limit of 5,000 requests per minute on the Start tier (https://platform.claude.com/docs/en/build-with-claude/token-counting [verified]). 12's tunables register carries a client token estimate divisor of 4 characters per token with the note that an under-estimate is the unsafe direction. That row is obsolete: the exact count is available at no cost.

**Prompt caching inside a batch is best effort, batch results are unordered, and the batch discount stacks with the cache multipliers.** Caching is supported inside the Batch API and the discounts stack, but "because batch requests process asynchronously and concurrently, cache hits are provided on a best-effort basis", with reported hit rates of 30 to 98 percent; the documentation advises identical `cache_control` blocks across the batch and the 1-hour TTL. "Batch results can be returned in any order", so results are matched by `custom_id` (https://platform.claude.com/docs/en/build-with-claude/batch-processing [verified]). And "These multipliers stack with other pricing modifiers, including the Batch API discount" (https://platform.claude.com/docs/en/about-claude/pricing [verified]), so a batch cache read on Opus 5 is $0.25 per MTok and not $0.50. 07's batch paragraph records the discount, the size limits and the expiry, and none of these four.

**Gemini's paid-tier data policy is now read.** "Google doesn't use your prompts (including associated system instructions, cached content, and files such as images, videos, or documents) or responses to improve our products" on the paid tier; on the unpaid tier "Google uses the content you submit to the Services and any generated responses to provide, improve, and develop Google products and services and machine learning technologies", and "human reviewers may read, annotate, and process your API input and output" (https://ai.google.dev/gemini-api/terms [verified]). Default log retention is 55 days, configurable to 7, 14, 28 or 55 (https://ai.google.dev/gemini-api/docs/logs-policy [verified]). 12 holds Gemini at second tier until the policy is read. It has been read, and the finding is a decision below rather than an open question.

One correction to 07's own figures. 07's Sonnet 5 permanence note is right: the scheduled 1 September 2026 increase to $3 and $15 "will not occur" [verified]. The per-model cache prices it derives only through the generic multipliers are printed on the pricing page and are tabulated in full below.
## The traffic model

Every cost claim below is against this denominator and no other. One student. Today is 2026-09-20 and the exam is 2027-05-10, which is about 230 study days.

**P1, live now.** The tutor role only, on one model. About one session a day, 15 to 25 items, 5 to 20 tutor calls a session. MCQ and short-answer grading is deterministic through SymPy and costs nothing. The composed sentence is cached on `attempts.tutor_sentence`, so a re-read of the feedback screen is free.

**P3.** The grader at 3 samples per judged point, invoked only in a unit check, a part drill, a mock or the six-week checkpoint, never in a micro-session (R10). The transcriber once per photographed page. The diagnostician on incorrect attempts.

**P4.** The generated bank. 139 active archetypes [measured, `python3 -c` over `data/archetypes.json`: 139 active of 144 records, 75 `no_calculator`, 37 `either`, 27 `calculator`, 83 with non-empty `point_types`, 103 with non-empty `official_examples`]. Each item is generated once and independently re-solved once.

A benchmark score is not a cost claim and nothing below substitutes one for the other. `04-item-generation.md` already argues that MATH-500 and AIME rank say little about grading a BC justification, and this document does not re-derive model quality from leaderboards.

**tutor, kept.** The routing stands. What does not stand is the configuration underneath it. 07's Anthropic trap list says "sending `thinking: {type: "enabled"}` to Opus 5 or Sonnet 5 returns 400, so an adapter written against the older shape fails on exactly the models this project routes to first", and `app/providers/anthropic.py` implements that as a blanket refusal of the `thinking` key. The live page says thinking is already on and needs no configuration on Sonnet 5 (https://platform.claude.com/docs/en/build-with-claude/thinking [verified]) and that thinking tokens are billed as output and count against `max_tokens` (https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost [verified]). `app/feedback/tutor.py:22` sets `MAX_OUTPUT_TOKENS = 400`. A one-paragraph tutor sentence is about 90 output tokens; a thinking pass on Sonnet 5 can consume the whole 400 before the paragraph starts, which returns `stop_reason: "max_tokens"` and an empty or truncated text while the operator is billed for the full 400. The correction is three settings, not a different model: `thinking: {"type": "disabled"}`, `output_config: {"effort": "low"}`, and `max_output_tokens` raised to 600 so a slip does not truncate.

**generator, kept.** 07's reason is "the prompt cache minimum of 512 tokens on Opus 5 is the lowest of the three major providers" and the 50 percent batch discount on both input and output. Both re-verified today (https://platform.claude.com/docs/en/build-with-claude/prompt-caching and https://platform.claude.com/docs/en/build-with-claude/batch-processing [verified]). Nothing outranks it. Effort is pinned at `medium` rather than left at the default `high`, for the reason in the cost model below.

**verifier, changed.** 07 routes the verifier to claude-opus-5, the same model as the generator. `04-item-generation.md` says, of the independent re-solve, "A second model, on a different provider where the routing allows it, receives the stem, the figure spec, and nothing else." `10-quality-and-evaluation.md` says "an audit failure with a flat escalation rate means the verifier is agreeing with the generator for a shared reason, which is the worst case, and is investigated as such." Routing both roles to one model maximises exactly the shared reason those two sentences name as the failure the pipeline exists to catch. The evidence 07 cites for the verifier row is about structured-output enforcement, cache minimum and batch discount, which is capability and cost evidence, not independence evidence, and it does not outrank the project's own stated worst case. Gemini's structured-output surface is a superset of Anthropic's on the keywords a verifier needs, including recursive `$ref`, `minimum` and `maximum` (https://ai.google.dev/gemini-api/docs/structured-output [verified]), and the paid-tier data policy that held Gemini at second tier is now read. The verifier's own output schema is an answer plus a solution path, which is shallow, so no schema capability is lost. The primary becomes `gemini-3.8-flash` on the Batch API at the paid tier; `claude-sonnet-5` on batch is the second deployment, which is still a different model from the generator. The measurement that would overturn this: the key error rate on the 100-item audit in `10-quality-and-evaluation.md` measured with a Gemini verifier against the same rate measured with an Anthropic verifier. If the Gemini verifier's disagreement rate with the generator is not higher than an Anthropic verifier's, the decorrelation argument bought nothing and the row reverts.

Corrected 2026-09-20 by `14-token-economy.md`: the Gemini tier moves down one step. The pricing page prints `gemini-3.5-flash-lite` at $0.30 input, $2.50 output and $0.03 cached input, with batch at half of each and no promotional end date beside those figures, against `gemini-3.8-flash` at $0.75 and $3.75 "through December 31, 2026" and $1.50 and $7.50 "starting January 1, 2027" (https://ai.google.dev/gemini-api/docs/pricing [verified, fetched 2026-09-20]). Flash-Lite's own model page prints "Structured outputs (Supported), Thinking (Supported)" and "Caching (Supported)", a 1,048,576 token input limit, a 65,536 token output limit, and the Batch API among its consumption options (https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite [verified, fetched 2026-09-20]), so the role loses no capability it uses. A verifier call falls from $0.003270 to $0.002058 and 6,178 blind re-solves fall from $20.20 to $12.71, a saving of $7.49 before 2027-01-01 and $27.69 after. The independence argument above is untouched: Flash-Lite is still a different provider from the generator, and every property that makes this role safe on a weaker model holds, because the answer is never trusted, it is compared under SymPy against a key three deterministic checks already agree on, and a disagreement routes to review rather than to publication. The measurement that would overturn the tier move: the disagreement rate with the generator on the same 500 items, Flash-Lite against 3.8 Flash, plus the 100-item audited key error rate.

**grader, kept.** 07 routes the grader to claude-sonnet-5, and the roles whose errors reach a student directly are named there as the grader, the verifier and the transcriber. Nothing found today outranks that. Effort is pinned at `medium` so it is a decision rather than a default.

Thinking stays on for the grader, and that decision is in tension with 07 and the tension is worth stating rather than hiding. 07 says the grader's temperature of 0 is not a tunable, because "a grader, a verifier and a transcriber that vary run to run make the agreement check meaningless, because the disagreement it detects would be sampling noise rather than genuine uncertainty". Thinking reintroduces run-to-run variance that temperature 0 alone does not, so two identically configured samples can disagree for a reason the detector was designed to exclude. It stays on anyway for two reasons. Judging whether a justification earns a rubric point is the one task in this system where intermediate reasoning most plausibly changes the answer, and `10-quality-and-evaluation.md` already treats a rising escalation rate as a healthy signal rather than a failure, because the design intent is that no single call is ever the final scorer of a free-response point. A point whose decision flips under a thinking pass is a point the operator should look at. **The measurement that would overturn it: the escalation rate with thinking on against thinking off, on the same golden set 2 responses whose intended score the operator has fixed.** If thinking-on escalates materially more without improving exact match against the fixed intended scores, the extra escalations are noise rather than uncertainty and thinking goes off for this role.

**diagnostician, changed.** 07 routes the diagnostician to claude-opus-5 and, in the same document, justifies Anthropic-first with "The roles whose errors reach a student directly are the grader, the verifier and the transcriber." The diagnostician is not in that list, and the grader, which is, is routed to the cheaper model. 07 therefore puts the most expensive model on a role its own justification does not name as highest stakes, while the role it does name runs on Sonnet. That is an internal inconsistency in 07, which is admissible evidence against the row without needing an external source. Two further facts point the same way. The diagnostician runs on incorrect attempts, so its call volume is session-scale, unlike the grader's, which is cadence-bound by R10; routing the highest-volume non-tutor role to the dearest model is backwards on cost. And the diagnostician's task is a probability-weighted ranking over a closed candidate set, since `03-diagnosis-and-feedback.md` restricts it to the BC-ERR and BC-MIS candidates reachable from the archetype's skills, and 07's own exhaustion behaviour already tolerates its absence by degrading to verification feedback. The primary becomes `claude-sonnet-5` at effort `medium`. The measurement that would overturn this: 11's diagnostician exit floor, two ranked hypotheses on at least 80 percent of diagnosed errors, plus the error-type recurrence rate after diagnosis that 12 names as the settling measurement. If Sonnet 5 misses the exit floor, the row reverts to Opus 5.

**transcriber, changed.** 07 routes the transcriber to claude-haiku-4-5. The vision page prints two resolution tiers: "High-resolution: Claude 4.7 and later models, max long edge 2576 px, max visual tokens 4784" and "Standard: All other models, max long edge 1568 px, max visual tokens 1568" (https://platform.claude.com/docs/en/build-with-claude/vision [verified]). Haiku 4.5 is in the standard tier. The same page warns that an image "might be resized if it is too large; this might, for example, make text less legible" (same URL [verified]). `10-quality-and-evaluation.md` records that in the cited 2026 AIED study "roughly 87 percent of remaining errors were transcription failures rather than rubric misapplication, with poor image quality, hallucinated content and mishandling of mathematically equivalent expressions as the named failure modes". Halving the linear resolution of a photographed page of handwritten calculus, on the one role whose dominant failure mode is misreading, to save less than a cent a page, is the wrong trade. A 3840x2160 photograph costs 1560 visual tokens on the standard tier and 4784 on the high-resolution tier (same URL [verified]); at Haiku 4.5's $1 per MTok input that is $0.00156 a page and at Sonnet 5's $2 per MTok it is $0.00957 a page, a difference of $0.008 a page (https://platform.claude.com/docs/en/about-claude/pricing [verified]). Two further facts reinforce it: Haiku 4.5's prompt cache minimum is 4,096 tokens against Sonnet 5's 1,024 (https://platform.claude.com/docs/en/build-with-claude/prompt-caching [verified]), so a transcriber prefix cannot realistically cache on Haiku; and Haiku 4.5 is absent from the effort parameter's supported-model list (https://platform.claude.com/docs/en/build-with-claude/effort [verified]), so there is no cost dial on it either. The primary becomes `claude-sonnet-5`. The measurement that would overturn this: golden set 3's expression-level exact match measured on both models over the same images. If Haiku 4.5 matches Sonnet 5 on the low-light and blur subsets, the row reverts and the saving is real.

**Secondary and offline rows.** The Gemini 3.8 Flash secondary is kept for every role, with one condition added: it must be the paid tier. On the unpaid tier "Google uses the content you submit to the Services and any generated responses to provide, improve, and develop Google products and services and machine learning technologies", and "human reviewers may read, annotate, and process your API input and output" (https://ai.google.dev/gemini-api/terms [verified]). A student's handwritten work and error history may not go there. The Ollama offline fallback for the diagnostician is kept on DeepSeek-R1-Distill-Qwen-14B: its official card still publishes MATH-500 pass@1 93.9 and AIME 2024 pass@1 69.7 under an MIT licence (https://huggingface.co/deepseek-ai/DeepSeek-R1-Distill-Qwen-14B [verified]), the Ollama 14b tag is a 9.0 GB download (https://ollama.com/library/deepseek-r1 [verified]), and the nearest same-size alternative, Qwen3-14B at 9.3 GB under Apache 2.0, publishes no benchmark numbers on its own card (https://huggingface.co/Qwen/Qwen3-14B and https://ollama.com/library/qwen3 [verified]), so it does not outrank the incumbent. Per-quantisation VRAM remains unpublished on Ollama's GPU page (https://docs.ollama.com/gpu [verified]) and stays an open measurement.

The characters-per-token divisor of 3.1 is the 4-characters-per-token rule of thumb raised by the 30 percent the pricing page attributes to the Claude 4.7 and later tokenizer [verified]. `app/providers/guard.py:58` uses 4, which under-estimates, and under-estimating is the unsafe direction for a cap.

**Bank sizing, which the first draft of this document got wrong.** 40 items per archetype is the *published* count, not the generated one. At an `[inferred]` 80 percent pass rate across the free checks and an `[inferred]` 90 percent pass rate at verification, publishing 40 needs `40 / (0.80 x 0.90) = 55.6`, so **56 generated per archetype, 7,784 generator calls and 6,227 paid re-solves**. Both survival rates are guesses and both are first-order drivers of the bank total.

**The arithmetic.** A cost in dollars is `tokens x rate / 1,000,000`. A role's total is the sum over its call classes of that product, with the prefix term as above.

**Tutor, worked in full.** Prefix 1,100, uncached input 174, output 90, one 1-hour write per session, 12 calls a session, 230 sessions. Per session: write `1,100 x 4.00 / 1e6 = $0.004400`; reads `11 x 1,100 x 0.20 / 1e6 = $0.002420`; uncached input `12 x 174 x 2.00 / 1e6 = $0.004176`; output `12 x 90 x 10.00 / 1e6 = $0.010800`. Session total `$0.021796`, cycle total `$5.01`. At 5 calls a session $2.65, at 20 calls $7.71.

**What the tutor costs as built.** `app/feedback/tutor.py:22` sets `MAX_OUTPUT_TOKENS = 400`, thinking is on by default, and the 529-token prefix does not clear the Sonnet 5 minimum so nothing caches. Per call `703 x 2.00 / 1e6 + 400 x 10.00 / 1e6 = $0.005406`, and `$0.005406 x 2,760 = $14.92`. The corrected configuration is $5.01. Decomposing the $9.91 gap: thinking disabled with the prefix still uncached is $6.36, so **$8.56 of the gap is the thinking configuration and $1.35 is the caching**. That ranking is the most useful number here, because `04-item-generation.md` and `07-ai-provider-layer.md` both name prompt caching as the honest lever and neither mentions thinking at all.

**Generator, worked in full, 56 per archetype on the Batch API at effort medium with `metadata` out of the schema.** 7,784 calls. Prefix written once per archetype at the batch 1-hour rate and read on the other 7,645: `139 x 3,900 x 5.00 / 1e6 = $2.71` plus `7,645 x 3,900 x 0.25 / 1e6 = $7.45`. Uncached input `7,784 x 100 x 2.50 / 1e6 = $1.95`. Output at 1,701 tokens `7,784 x 1,701 x 12.50 / 1e6 = $165.51`. Total **$177.62**.

## Bank size

**Decision: 40 verified items per archetype, 139 x 40 = 5,560 items, and the draw rule changes from uniform random to least recently served within the archetype.** The bank size is `[inferred]`; the draw-rule change is what makes it the right number rather than an arbitrary one.

The traffic arithmetic. 230 sessions at 15 to 25 items is 3,450 to 5,750 item serves over the cycle, midpoint 4,600. Spread uniformly over 139 archetypes that is 24.8 to 41.4 serves per archetype, midpoint 33.1. Under a concentrated draw where the top decile takes half the traffic, the top 14 archetypes take 164 serves each and the other 125 take 18.4 each. The concentrated figure is a stipulation, not a measurement.

The measured part, and its limit. The shipped simulation runner was run read-only over all six trajectory fixtures for 230 days with the bank forced to 60 per archetype [inferred: the run's command was not recorded, so its figures are held as a report rather than a measurement until it is rerun]. It served 1,312 to 2,961 items per simulated student and reached 7 to 11 archetypes, with one archetype taking 13 to 32 percent of all traffic. That last figure is the useful one: the draw is strongly non-uniform even inside a small archetype world. The rest does not transfer, because `tests/fixtures/graph_p1.json` holds 13 archetypes rather than 139, which inflates per-archetype load by about 10.7 times, and because the fringe empties so total traffic falls below the plan's 15 to 25 items a day. This document does not use the fixture's per-archetype serve counts as evidence for the bank size and says so rather than dressing them up.

Why the draw rule is the lever and the bank size is not. `app/engine/select.py:143` filters a 7-day recently-served exclusion set and then picks uniformly at random from what remains [verified, by reading that line]. Under a uniform random draw the chance of an immediate repeat is `1/B`, and never seeing an identical item twice over `n` serves is a birthday problem: at `n = 33`, 95 percent no-repeat needs a bank of 10,560 items per archetype, and at `n = 164` 264,522, by the exact birthday product [measured: the `draw.bank_for_no_repeat` lines of `python3 tools/cost_model.py`]. No affordable bank buys zero repeats under the shipped rule. Under a least-recently-served draw the answer is simply `B >= n`. In closed form, with the expected number of distinct items under a uniform draw being `B x (1 - (1 - 1/B)^n)` [measured: the `draw.repeat_share` lines of the same command]: at `n = 33` serves, a bank of 30 gives 38.8 percent repeated items under random and 9.1 percent under least recently served; a bank of 40 gives 31.4 percent under random and 0.0 percent under least recently served. The 7-day exclusion lowers the random figures slightly and does not change the ordering. One line of selection code moves the metric further than 50 percent more generation spend does.

Why 40 and not 30 or 60. 40 is the smallest bank that covers the uniform-traffic per-archetype load of 33 with margin under the least-recently-served rule, which is the rule this document adopts. 30 leaves 9.1 percent of serves as second exposures. 60 buys nothing above 40 at uniform traffic and still leaves 63.4 percent repeats on a top-decile archetype at 164 serves [measured: `draw.repeat_share_lrs_bank_60_at_164`], so it does not solve the case it would be bought for.

Why a second exposure is worth avoiding, with numbers. Retest gain is larger on identical than on alternate forms: standardised mean change 0.372 with a 95 percent interval of 0.317 to 0.427 on N = 146,173 for identical forms against 0.226 with an interval of 0.165 to 0.288 on N = 7,012 for alternate forms, a difference of about 0.15 standard deviations, and the inflation decays at roughly 0.0008 standard deviations per week (https://gwern.net/doc/iq/2018-scharfen.pdf [verified]). Varied retrieval beats repeating an identical item on transfer: 0.64 against 0.52 with t(31) = 2.77, p = .009, d = .49, while practice accuracy on the repeated identical item climbs 0.58 to 0.92 to 0.95 against 0.62 to 0.68 to 0.66 for varied practice (https://static1.squarespace.com/static/5c8baca1e5f7d136349ea789/t/5e739a3d46338e7dec37aaf6/1584634429337/Butler+et+al+2017.pdf [verified]). The second curve is the one that matters here, because it is exactly the accuracy this engine would be crediting as unaided successes. `12-open-questions.md` sets the simulation acceptance threshold at 5 percent false-mastery declarations, so a 9.1 percent second-exposure rate sits on top of the entire error budget.

Two guards go with the number, and both are free. First, the three credited unaided successes in the mastery rule must come from three distinct item ids. `app/engine/update.py:405` records the archetype id and the day and never the item id [verified, by reading that function], and `02-adaptive-engine.md` records that 440 of the 522 skills any active archetype lists sit in exactly one archetype, so for 84 percent of skills the corroboration rule collapses to one archetype and the identical item served on day 0, day 8 and day 16 satisfies every condition. Second, `REPEAT_WINDOW_DAYS = 7` at `app/engine/constants.py:69` appears in no plan document and in no test [measured: `grep -rn REPEAT_WINDOW_DAYS docs/plan/0* docs/plan/1[0-2]* tests`, no match; this document is the first to name it]; it is the only mechanism bounding repeat exposure in the product and it is undocumented and unasserted. It belongs in 02 with a test.

The exposure-control literature was read and is deliberately not used to set this number. The conventional maximum item exposure rate in computerised adaptive testing is 0.20, described as "a common control condition" (https://pmc.ncbi.nlm.nih.gov/articles/PMC10664747/ [verified]), and sweeps run it from 1.00 down to 0.09 (https://pmc.ncbi.nlm.nih.gov/articles/PMC7174806/ [verified]), with the position that no single value is defensible a priori and overlap is the better metric (https://personal.unizar.es/barrada/papers/10_APM_Barrada.pdf [verified]). All of it is about test security across many examinees, which is not this problem, so it is cited to show that the field sets these numbers by simulation per pool rather than to borrow one.

**The one measurement that would overturn 40: the 95th percentile per-archetype serve count over the first 60 days of real use, projected linearly to 230 days.** Above 120, 40 is too low and the number becomes that percentile for the archetypes above it. Below 40, drop to 30. The bank is therefore generated in two waves rather than one: a first wave of 28 generated per archetype for all 139, which publishes about 20 at the assumed survival rates, while the measurement accumulates, and a second wave of 28 driven by the measured distribution. Each wave costs $90.10, so that stages $90.10 of the $180.19 behind a number rather than a guess, at the $2.57 premium the staging paragraph above prices, and it is the same discipline `10-quality-and-evaluation.md` applies to the key error rate threshold.

## Prompt caching, per role

The rules that bind. The minimum cacheable prefix is 512 tokens on Opus 5, 1,024 on Sonnet 5 and 4,096 on Haiku 4.5, and below the minimum "shorter prompts are processed without caching and without an error"; at most 4 explicit breakpoints per request, with automatic caching consuming one; a cache hit requires a byte-identical prefix; the 5-minute lifetime is measured from the start of the request that writes or reads the entry (https://platform.claude.com/docs/en/build-with-claude/prompt-caching [verified]). Changing the thinking configuration, the resolved effort level or `output_config.format` invalidates the cache (https://platform.claude.com/docs/en/build-with-claude/thinking and https://platform.claude.com/docs/en/build-with-claude/structured-outputs [verified]). Gemini's implicit cache minimum is 4,096 tokens on the 3.x Flash line (https://ai.google.dev/gemini-api/docs/caching [verified]).

Haiku 4.5's 4,096-token minimum still binds on one role. The transcriber moved off Haiku 4.5, but the safety section below adopts a Haiku 4.5 classifier between the transcriber and the grader, and that call's prefix will not reach 4,096 tokens at any sensible length. It is priced uncached and should be.

Three things must never sit above a breakpoint, and none of the reasons is cost. The student's response text, because it varies per call and would destroy the hit rate. The item's key, on any verifier call, because the verifier's blindness to the key is structural and a cached prefix is a place a key could be smuggled in. And anything that changes when a template version changes without the version changing, because a silently drifting prefix produces a cache miss the metric cannot explain.

**TTL: 1 hour on every role that caches at all.** The 1-hour write costs 2x base input against the 5-minute write's 1.25x, so it pays after two reads rather than one [verified]. The tutor, the grader and the diagnostician all make several calls inside a session spanning more than 5 minutes, so a 5-minute entry would expire between calls and be rewritten, which is the failure the brief names: a sparse caller paying the premium without earning the reads back.

**The floor is three calls in an hour**, and the arithmetic is worth stating because an earlier draft of this document got it backwards. Under a 1-hour TTL, three calls are one write and two reads, `2.0 + 0.1 + 0.1 = 2.2x` base against `3.0x` uncached, so caching wins. Two calls are one write and one read, `2.1x` against `2.0x`, so caching loses. Three is the floor, not the exclusion.

**On the tutor specifically the break-even is 5 calls a session, not 3**, because the cached configuration also grows the prefix from 529 to 1,100 tokens to clear the Sonnet 5 minimum, and those extra tokens have to be paid for somewhere. At 5 calls the two configurations cost $2.65 either way; at 6 the cached one is $2.99 against $3.18; below 5 it loses [measured: the `tutor.uncached_at` and `tutor.cached_at` lines of `python3 tools/cost_model.py`]. The brief's range is 5 to 20 tutor calls a session, so caching is a wash at the floor and a clear win across the rest.

**The tutor's prefix is grown, not padded.** Growing a prompt with filler to reach a cache minimum makes the prompt worse to save $1.35. What goes in earns its place: the guardrail-level definitions for all levels rather than the current one, the notation and rendering rules the sentence must obey, and the student's persistent misconception list, which `07-ai-provider-layer.md` already says belongs in the prefix because it is slow moving. If those four together still do not clear 1,024 tokens measured with `count_tokens`, the breakpoint is removed rather than the prompt padded.
## Batching

What goes to a batch endpoint: generation, independent verification, the golden set 1 eval, and any grading that has already missed its interactive window. What never does: the tutor, the transcriber, and any grading a student is waiting on, because all three batch endpoints expire at 24 hours and nothing a session needs may depend on a 24-hour deadline (https://platform.claude.com/docs/en/build-with-claude/batch-processing, https://developers.openai.com/api/docs/guides/batch and https://ai.google.dev/gemini-api/docs/batch-mode [verified]).

**Batch ordering, so the per-archetype prefix is actually reused.** The documentation is explicit that batch requests process asynchronously and concurrently and that cache hits inside a batch are best effort, with reported hit rates of 30 to 98 percent; its own advice is identical `cache_control` blocks across the batch, a steady stream, and the 1-hour TTL because a batch runs longer than 5 minutes (https://platform.claude.com/docs/en/build-with-claude/batch-processing [verified]). The consequence for this project is a specific shape. One batch per archetype, not one batch spanning the bank, so that every request in a batch shares one prefix byte for byte. The prefix is warmed by a single ordinary non-batch call before the batch is submitted, because `max_tokens: 0` cache pre-warming is rejected inside a batch (same URL [verified]), and the batch is submitted inside the hour. Archetypes are submitted one after another rather than all at once, so a concurrent batch of a different archetype is not competing for the same cache slots. And the cache hit rate is read back per batch from `cache_read_input_tokens` and recorded, because at 30 percent the generation cost is materially higher than the table above and the operator should see it rather than infer it.

**Failure modes at the documented limits.** A batch holds at most 100,000 requests or 256 MB, whichever binds first, and an oversized batch returns 413 `request_too_large` (same URL [verified]). A per-archetype batch of 40 items is four orders of magnitude inside both, so the size limits are not a real risk here and the job builder's chunking is insurance rather than a constraint. The real failure modes are three. Results come back in any order and must be matched by `custom_id`; a job builder that assumes input order writes item B's key onto item A, which is a silent key error and the exact defect `10-quality-and-evaluation.md` calls the most damaging one the product can ship. A batch that does not finish inside 24 hours expires, its unfinished requests are cancelled, the completed outputs remain downloadable and only the completed requests are billed, so the retry has to be driven off the per-request result type rather than off the batch status. And `stream: true`, the `speed` parameter and `max_tokens: 0` are all rejected inside a batch, so a code path shared with the interactive adapter has to strip them.

The Message Batches API carries its own rate limits, 1,000 requests per minute and 200,000 maximum queued batch requests on the Start tier (https://platform.claude.com/docs/en/api/rate-limits [verified]). A full bank pass at 56 generated per archetype is 7,784 generation requests and 6,227 verification requests, well inside the queue limit, so the bank can be generated in one sitting if the credit exists.

## Verification pipeline ordering

`04-item-generation.md` lists five checks and requires unanimous agreement to publish. Four are free local computation and one, the independent re-solve, is a paid model call. 04 lists the paid one first. The ordering below is cheapest first and changes nothing about what publishes.

**Stage 0, once per archetype, before any item is generated.** The Monte Carlo family pass. 04 describes it as "a few hundred parameter tuples are drawn from the archetype's parameter spec, the solution path is run symbolically on each, and the `invariants` from the spec are asserted throughout", and the P1 gate is zero failures on 300 draws. It is a property of the parameter spec, not of an item, so running it per item repeats one archetype's work 40 times for no information. It runs once per archetype per spec version and an archetype that fails is quarantined and generates nothing. Also in stage 0: the archetype's declared `point_types` against the step count of its `expected_solution_path`, because 12 of the 83 archetypes with non-empty `point_types` list more point types than solution-path steps [measured: `python3 -c` over `data/archetypes.json`, comparing `len(point_types)` with `len(expected_solution_path)` on the 139 active records, rerun 2026-09-20 with the same result], and every item generated from one of those 12 trips rejection rule 9 for a library reason rather than a generation reason.

**Stage 1, free, per item, in this order.** Schema validation against the item output schema, which settles rejection rules 7 and 13 in microseconds. The parameter-draw constraint predicates, rejection rule 1. The calculator-boundary assertion, rejection rule 8, which is structural rather than mathematical: a `no_calculator` item whose verified path needs numeric root-finding is a mis-filed item. Distractor equality against the key and against each other, rejection rules 5 and 6, which `app/items/verify.py:180` `distractor_checks` already implements.

**Stage 2, free, per item, and the one 04 does not list.** The generator's own key against the generator's own worked solution. 04 requires MathJSON on the last worked-solution step, and `BUILD-LEDGER.md` calls that step "the second statement of the key that the SymPy and numeric checks compare against". `app/items/mathjson.py` `to_sympy` and `app/items/verify.py` `equivalence` already do this comparison. It is free, it runs before any paid call, and it kills the class of item where the model's solution contradicts its own key. It is stage 2 rather than stage 1 only because a SymPy simplification can take seconds where a schema check takes microseconds.

**Stage 3, near free, per item.** The duplicate gate, MinHash Jaccard over 5-grams first because it is local, then the embedding cosine only on what survives. An embedding call is the cheapest paid call in the system at $0.20 per 1M tokens for Gemini Embedding 2 text (https://ai.google.dev/gemini-api/docs/pricing [verified]), but ordering the local stage first still removes most of them.

**Stage 4, paid.** The independent re-solve, on a verifier that has never seen the key.

**Stage 5, free.** SymPy equivalence and numeric evaluation of the re-solve's answer against the candidate key, and the publication rule.

**The spend avoided, computed rather than asserted.** One verifier call at the recommended routing is priced uncached, because its prefix of about 1,100 tokens is below Gemini's 4,096 implicit minimum: input of `1,220 x 0.375 / 1e6 = $0.000457` and output of `1,500 x 1.875 / 1e6 = $0.002812`, so `$0.00327` per call. At an `[inferred]` 20 percent failure rate across stages 1 to 3, a 7,784-call pass avoids `0.20 x 7,784 x $0.00327 = $5.09`. Stage 0 avoids more per occurrence: an archetype with a defective parameter spec would otherwise generate and verify 56 doomed items at `56 x ($0.0228 + $0.00327) = $1.46`, so ten such archetypes are $14.61. The honest total is $5.09 to $19.70 on a $177.62 bank pass, which is 2.9 to 11.1 percent.

That is not why the ordering matters. It matters because an item whose own worked solution contradicts its own key, published into stage 4, arrives as a verifier disagreement. `10-quality-and-evaluation.md` uses the escalation rate as its health signal and says a raised key error rate "should show up first as a raised escalation rate". If self-contradictory items are allowed to reach the verifier, the escalation rate measures generator incoherence and verifier disagreement mixed together, and the signal that is supposed to detect a correlated generator-verifier failure stops being readable. Cheapest first is a cost decision that happens to be free; stage 2 before stage 4 is a measurement decision that is not optional.

## Generation output volume

The premise that the worked solution is the dominant output term does not survive measurement. On a record built to 04's full output schema for BC-QA-02011, four steps, multiple choice, no figure: 2,286 characters total, of which `worked_solution` is 594 (26.0 percent), `metadata` is 732 (32.0 percent) and stem, options and key together are 960 (42.0 percent) [measured: `python3 -c` over a hand-built full-schema record, recorded in the research ledger]. The `metadata` block is larger than the worked solution. The P1 fixtures give a lower worked-solution share, 0.183 to 0.213 [measured over `tests/fixtures/items_p1/*.json`], because all 36 carry two-step solutions with no point-type tag, no rule name, no `sympy` and no metadata block, so they understate P4 rather than describing it. The share rises with step count and format: 0.260 at four steps as multiple choice, 0.346 at six, 0.354 at four as free response, 0.522 at eight [single-source: the same hand-built record extended by hand, not kept in the repository], and only 2 of 139 archetypes carry eight or more steps [measured: `python3 -c` over `data/archetypes.json`]. The mean `expected_solution_path` length is 4.22 steps over 139 active archetypes [measured: `python3 -c` over `data/archetypes.json`].

**Decision one: `metadata` leaves the generator's output schema.** Every field in it is an echo of the generation request. `archetype_id`, `variant_id`, `difficulty_settings`, `representation`, `calculator_status` and the whole `provenance` block are all known to the caller before the call is made, and having the model restate them risks the model restating one wrongly. The backend writes them. In 04's output schema, `metadata` moves from `required` to absent and the `required` list becomes `["stem", "key", "worked_solution"]`.

What it is worth is smaller than 32 percent, and saying so is the point. The measured `metadata` block is 732 characters, which at 3.1 characters per token is **236 tokens**. A generator call at effort medium emits about 501 visible tokens and about 1,200 thinking tokens, so removing `metadata` removes 236 of 1,701 billed output tokens, **13.9 percent**. Measured on the bank pass: $200.58 with `metadata` against $177.62 without, a saving of **$22.96**, while moving effort from `high` to `medium` saves **$126.49** on the same pass. The schema is the smaller lever by a factor of 5.5 and both are worth taking. The measurement that would overturn decision one: none. Every field is known to the caller and there is no measurement under which having the model restate them is better.

**Decision two: the per-item worked solution stays model output, and 04 gains a rejection rule instead of a template system.** The case for computing it symbolically was built and tested rather than argued. 108 of the 139 active archetypes have a step sequence fixed for every draw: 73 with a fixed prose skeleton, 15 where one step's prose switches on a computed outcome, and 20 where a step is included or dropped by a difficulty dial the backend already sets; the remaining 31 have a step sequence that depends on the drawn values, and three of those are method-selection archetypes where naming the technique is the whole item [measured, by hand labelling all 139 `expected_solution_path` lists; the labels themselves are `[inferred]` judgements about prose]. A working proof of concept over three of the easiest archetypes, 200 draws each, produced mathematically correct steps on all 600 draws and structurally well-formed LaTeX on all 2,600 rendered steps [single-source: a proof of concept not kept in the repository; `tools/template_trial.py` is the later, model-authored trial and is measured separately]. It also produced a doubled sign on 8.5 and 10.1 percent of rendered steps, a vacuous step on 4.5 percent of draws where the tangent slope came out zero, and required a hand-written LaTeX assembler per archetype because SymPy's default printer distributed a point-slope form into slope-intercept and dropped the absolute values inside a logarithmic antiderivative [single-source: the same proof of concept]. The authoring cost is 586 step prose templates plus roughly 2,500 lines of LaTeX assembly, against a token saving of about $15 across the bank once `metadata` is already gone.

That trade is the wrong way round when a human writes the templates. The scarcest resource in this project is the operator's authoring time, which already owes 130 hand-authored items, five open P1 gates and three golden sets.

The real finding in that investigation stands on its own and is adopted. None of 04's fourteen rejection rules checks that a worked-solution step is mathematically correct; rule 9 checks only BC-PT tagging consistency. Under 04 as written, the key is verified three ways and the worked solution the student reads on the feedback screen is unverified model output. **04 gains rejection rule 15: every worked-solution step that carries a `sympy` expression must follow from the previous step's under the rule the step names, checked with `app/items/verify.py` `equivalence`, and a step that is an identity under the drawn parameters is a vacuous step and is rejected.** 04's step schema already carries a `sympy` field described as "Parseable expression for the verifier", which is the hook this rule uses; 04 never mentions MathJSON, and an earlier draft of this document wrongly attributed that requirement to it. MathJSON appears in `10-quality-and-evaluation.md` and `11-phased-delivery.md`, for hand-authored P1 items.

**The one measurement that would overturn decision two: the model's per-step defect rate on the 100-item audit that D12 already requires at P1 exit.** The templated approach measured at 8.5 to 10.1 percent of steps carrying a surface defect and 4.5 percent of draws vacuous. If the model's per-step defect rate comes in above that, templating wins on quality and the authoring cost has to be paid. That number does not exist anywhere in the repository, and the cheapest way to get it is to add a per-step defect count to the audit the operator is already going to run.
## Radicals and incidentals

The template trial rests on a premise that the psychometric literature has tested and rejected: that instantiations of one template share a difficulty. They do not, and the gate has to say which parameters may move without moving the difficulty rather than assume none of them does.

**The finding, from primary sources.** Fu, Choe, Lim and Choi (2022), Educational Measurement: Issues and Practice 41(2), found 9 of 23 templates isomorphic on the first pass and 9 needing major modification [single-source]. Sam et al. (2023), BMC Medical Education 23:620, found 20 of 50 item models with a facility spread above 0.15 across their variants at n = 2,218 [single-source]. Sommer and Arendasy (2025), Journal of Intelligence 13(8):102, report 10 to 30 percent item loss after calibration of generated items [single-source]. Tian and Choi (2023), Applied Psychological Measurement 47(4), show that ignoring within-family variance biases ability estimates toward the centre and that lengthening the test does not remove the bias [single-source]. On what moves difficulty, Embretson and Daniel (2008) over 101 operational mathematics items: distractor evaluation b = 0.999 logits and having to construct the equation b = 0.663, both significant; computation count b = -0.024, procedural level b = 0.039 and equation recall b = -0.065, none significant [single-source]. More arithmetic does not make an item harder; a different path or a different distractor set does.

**Consequence one, the template contract.** Every parameter declares a role, `radical` or `incidental`, in Bejar's terms. An incidental changes the numbers and nothing else. A radical changes what the solver has to do. The declaration is checked, not trusted: `tools/template_trial.py` `incidental_check` takes a base draw, varies each declared incidental alone over its whole domain (or a sample of 32 values when the domain is larger), and compares the structure of every step's value and of the key, where structure is whether the value is zero, its head, the functions it contains, its degree in the free symbol when polynomial, and its arity. An incidental that moves any of those fails the template with the named defect `incidental_changes_path`, and a parameter with no role fails it with `parameter_role_undeclared`. The sign of a number is deliberately not structure, because a negative slope is solved as a positive one is; a zero is, because it deletes a term. Distractor composition is a radical by construction, and the report lists it as one: the current templates generate distractors by rule and the earlier draft of this document treated that as free, which Embretson and Daniel's largest coefficient says it is not. The proof that each check fires is in `tests/tools/test_template_trial.py`, one mutation of the clean fixture per check.

**Consequence two, the gate as extended on 2026-09-20, and what it measures.** The gate now runs eleven checks on every template over 300 seeded draws: LaTeX balance, doubled signs, math-mode presence and vacuous steps as a surface rate under 2 percent; key disagreement at zero; the key not a copy of the last step; no draw raising; a draw space of at least 2,000; a declared representation from the archetype's list, with a figure spec when that representation is graphical, tabular, a slope field or a diagram; every distractor's `error_path` an active BC-ERR id; every `point_type_id` a BC-PT id; exactly four options; and the parameter roles above. Re-run over the 26 templates in `var/` [measured: `.venv/bin/python` over `tools/template_trial.py` `run_draws` for every file under `var/template_*/`, 2026-09-20]: **0 of 26 pass**. On the six checks the gate had before, 12 of 26 pass, which is the honest restatement of the earlier "6 of 18" and "7 of 8" claims once the key-copy detector runs on all of them. The failures by check: 26 declare no representation, so the figure check cannot fire on any of them; 26 carry at least one `error_path` that is prose rather than a BC-ERR id, and in fact 0 of their distractors resolve; 14 carry four distractors against 04's four options; 6 tag a step with an id that is not a BC-PT id, two of them BC-SKL ids; 13 copy the key from the last step; 1 disagrees with its own key. The role declaration is absent on all 26 by construction, because the schema did not have it when they were generated. None of this is a model finding yet; it is a contract finding, and the prompt now carries the allowed BC-ERR ids, the representation list and the role instruction so the next run can be one. The measurement that would overturn the contract additions: none. Each check enforces a rule 04 already states.

**Consequence three, the difficulty prior.** `02-adaptive-engine.md` assigns one declared prior per archetype and one fixed 0.4-logit variant shift. The decision, recorded in 02 under Variant adjustment: the prior does not gain a within-archetype variance term. It states instead that it accepts a known centre-ward bias in `p_A` on generated items, because a variance term set with no per-instantiation data is a second guessed parameter on top of a first, and Tian and Choi's result is that the bias is an estimation-side effect that a term of unknown size cannot be trusted to remove. The measurement that overturns it: first-attempt accuracy per template, segmented by instantiation, once any template has 30 or more attempts across at least 5 instantiations. If the facility spread across instantiations of one template exceeds 0.15, which is Sam et al.'s threshold, that template's incidentals are not incidental and the term is added with that measured spread as its first value.

**The seam decision: instantiate at build time, into the `items` table.** Two designs were open. Materialise every instantiation as an `items` row when the bank is built, or hold templates only and instantiate at serve time. Build time wins, for four reasons that are each sufficient. `attempts.item_id` is a permanent reference: `load_attempts_history` joins it to `items` for the archetype, `submit_attempt` grades against the stored key by it, and `read_feedback` renders the worked solution by it, so a serve-time instantiation needs a new durable table anyway and three rewrites to point at it. Verification is per item and paid: 04's independent re-solve, the duplicate gate and the provenance record all key on one concrete stem and key, and a serve-time draw would either run a paid verifier call inside a session, which the batching section forbids, or serve an unverified draw, which the quality floor forbids. The requeue rule serves the same item id again after a corrected error note, which needs the item to exist tomorrow exactly as it did today. And the least-recently-served draw rule needs a stable set of ids to be least recent over. What build time costs is storage and the loss of an unbounded draw space, and neither binds: 56 rows per archetype is 7,784 rows, and the 2,000-tuple floor exists so 56 can be drawn without a repeat. The measurement that would overturn it: a measured repeat-exposure rate on real serves that stays above 5 percent at 40 published per archetype, which would mean the bank is too small rather than the seam wrong, and the answer is to instantiate more, not to instantiate later.

## Structured outputs, streaming and latency

The Anthropic surface, re-read today. `output_config.format` takes `{"type": "json_schema", "schema": {...}}`. Supported keywords: the six JSON types plus null, `enum`, `const`, `required`, `additionalProperties` when set to `false`, `anyOf`, `allOf` with limitations, `$ref`, `$defs`, `definitions`, `default`, the string formats, and `minItems` only at 0 or 1. Rejected with a 400: recursive schemas, complex types inside an enum, external `$ref`, `minimum`, `maximum`, `multipleOf`, `minLength`, `maxLength`, array constraints beyond `minItems` of 0 or 1, `additionalProperties` set to anything but false, and `allOf` combined with `$ref`. The compiled grammar is cached 24 hours from last use and is invalidated by a change to the schema structure or to the set of tools, but not by a change to a `name` or `description` field. Changing `output_config.format` invalidates the prompt cache (https://platform.claude.com/docs/en/build-with-claude/structured-outputs [verified]).

04's claim that its schemas avoid `minimum`, `maximum` and recursion so that one schema serves both Anthropic and Gemini holds against the current keyword list. One thing does not: `additionalProperties` is absent throughout 04's `GeneratedItem` schema, and whether strict enforcement holds when the keyword is omitted is unknown from the loaded page. Setting it to `false` on every object is free, is supported on both providers, and removes the question.

`app/providers/anthropic.py:85` sends `{"format": {...}, "strict": True}`, putting `strict` inside `output_config`. On the live page `strict` appears only on tool definitions and never inside `output_config` (same URL [verified]). No P1 role sets a schema so the line has never executed; the P4 generator and verifier are the first callers and would be the first to find out.

| Role | Schema | Strictness | What a schema change costs |
| --- | --- | --- | --- |
| tutor | None | n/a; the output is prose rendered as KaTeX-safe text | n/a. This is also why no student ever waits on a grammar compilation |
| generator | The `GeneratedItem` schema, `additionalProperties: false` throughout | Required | Invalidates the prompt cache for every archetype prefix and pays a grammar compilation on first use. A schema bump is therefore a bank-wide cache-warming event and is released at a batch boundary with a `prompt_version` bump, never trickled |
| verifier | Answer plus solution path | Required | Small and cheap to change; on the Gemini primary this is `responseSchema`, which is a superset of the keywords used |
| grader | Earned, rationale, rule cited, one object per BC-PT | Required | Invalidates the grader prefix. Released at a session boundary, because a mid-session change would split one student's grading across two schema versions |
| diagnostician | BC-ERR list, BC-MIS with probabilities, `mastery_state` per skill | Required | As the grader |
| transcriber | Structured transcription for rendering | Required | As the grader |

**Streaming earns its complexity on exactly one role: the tutor.** It is the only role whose text a student watches arrive. The grader streams progress only, per 07, which is a user-interface concern rather than a provider one. The generator and the verifier run in batches where `stream: true` is rejected outright. The diagnostician and the transcriber produce structured output that is useless until complete. So one streaming path, not six, and it is the path `app/providers/anthropic.py:45` gets wrong today: it sets `"stream": true` in the body and then hands the response to a transport that calls `json.loads` on it, which cannot parse an SSE response. No test catches it because every test injects a fake transport that returns a dict.

**Latency.** The lowest-latency configuration available on Sonnet 5 for the tutor is thinking disabled with effort `low`, which is the same configuration the cost model chose, so latency and cost point the same way on the one interactive role. Nothing else in the system is on a path a student waits on: the bank is pre-generated, grading is queued when it cannot run promptly, and the transcriber runs behind a read-back confirmation the student is already looking at.

## Budget, fallback and degradation

**The hard-stop table in 07 is right in its ordering and incomplete in its coverage.** The ordering principle, that the caps degrade support before they degrade correctness and never degrade correctness silently, is correct and nothing here relaxes it: a verifier at its cap means fewer new items and never an unverified item served. Three rows are missing.

A role with no configured cap. Today `app/providers/guard.py:439` raises `BudgetStopped` with the cap named `unconfigured`, before any budget row is created and without writing an audit entry [verified, by reading that function and `tests/providers/test_guard.py::test_a_role_with_no_configured_cap_is_refused`]. The refusal is right; the silence is not, because 07's own rule is that "a role that has stopped says so where it stopped rather than only in settings". An unconfigured role is refused, the refusal is audited once per user per role per day, and the settings screen shows the role as unconfigured rather than as stopped.

A cap that is raised after a stop. `_apply_caps` at `app/providers/guard.py:452` writes the new cap values and leaves `hard_stopped` at 1, so raising a cap far above the day's spend still refuses with `cap="hard_stopped"` [verified, by reading `_apply_caps`], while the method's own docstring says "An operator who lowers a cap has it bind on the next call rather than tomorrow". Raising a cap above the day's recorded spend clears the stop.

A per-session ceiling. `09-security-and-privacy.md` names a per-session call ceiling and a per-item tutor ceiling as inferred tunables with no number. The number is 20 tutor calls per session and 3 per item, matching the upper bound of the traffic model this document is costed against, and the per-item ceiling exists for the learning reason 09 gives as much as the cost one.

**Where `app/providers/guard.py` is wrong.** Read in full. The pricing arithmetic is correct against the live table: 5.00 x 1.25 = 6.25, 5.00 x 2 = 10.00, 5.00 x 0.1 = 0.50, and the same on Sonnet 5. Nine things are not.

1. **The price table cannot serve the routing.** `MODEL_PRICES` at line 75 holds `claude-opus-5` and `claude-sonnet-5` only, and `price_for` at line 107 raises on anything else. The transcriber no longer routes to Haiku 4.5, which an earlier draft gave as the reason; the defect stands on the Gemini secondaries and the screen instead. **Fallback and degradation, unchanged from 07 except where the above forces it.** Every per-role exhaustion behaviour in 07 stands. ## Evals

Which of `10-quality-and-evaluation.md`'s model-output evals discriminate, what one run costs, and the cheapest schedule that still catches a regression before a student sees it.

**Golden set 1, generated items, half discriminates and half will flake.** 07 sets the generator temperature to 0.7 and `app/providers/anthropic.py` sends no seed [verified, by reading `_wire_body`], so there is no replay: re-running generation against a frozen parameter draw produces a different item each time. That is now doubly true, because a non-default temperature is a 400 on the routed models at all, as recorded above. Split 10's four assertions by robustness. The key being mathematically equivalent to the golden key under SymPy is temperature-robust, because the frozen draw fixes the numbers and therefore the correct answer, and it catches the defect 10 calls the most damaging the product can ship. The calculator boundary holding is likewise a property of the produced item. The other two, that the solution path matches `expected_solution_path` step for step and that every distractor maps to the BC-ERR path recorded on the golden item, are identity assertions against one sample and will go red without a regression. They also contradict 07's own template rule that "the properties asserted are structural rather than textual, because asserting exact model output would be a test of the model rather than of the template". Those two are re-expressed structurally: the solution path hits the same ordered set of point-type tags, and every distractor resolves to some BC-ERR id reachable from the archetype's skills rather than to one frozen id.

**Golden set 2, FRQ grading, is the only eval that is genuinely the last line before a student.** The literature 10 cites gives large effect sizes between prompting regimes, kappa 0.22 naive against 0.56 for CARO, so a template change that dropped the eligibility-after-error clause would move aggregate exact match well past the noise floor. What it misses: it is adversarial by construction, so it says nothing about the rate at which the grader is right on ordinary work. And one of its four metrics is not computable as specified. 10 defines the set as 5 responses on each of at least 30 BC-PT ids, which are point types, and then asks for mean absolute error on a question total out of 9. A nine-point total does not exist unless responses are grouped into whole questions. Either the set gains that grouping or the metric goes.

**Golden set 3, transcription, is the best discrimination per dollar in the plan.** At temperature 0 against a fixed image set and a fixed operator transcript, character-level and expression-level exact match is a real detector, and it is the only thing in the plan that would notice an image-pipeline change, meaning a re-encode, a downscale or a quality-gate threshold move. Its second metric, "the rate at which a wrong read-back would have changed a point decision", which 10 calls "the number that actually matters", is not computable either, because golden sets 2 and 3 are independent collections and no point decision is attached to a golden-set-3 image. Link them or drop the metric.

**Leniency calibration does not discriminate and costs nothing.** 10 already concedes it: reported as a direction and a magnitude, never as a pass or fail on its own. It is an analysis over gradings golden set 2 has already produced, so its marginal model cost is zero. It attaches to golden set 2's full run, is never scheduled separately and is never gated on.

**Cost per run, from the same token table.** Golden set 1 replays generation for 139 items at the generator's own per-item cost of `$177.62 / 7,784 = $0.0228`, so `$3.17` a run on the Batch API. **Cohen's kappa at 5 by 30 cannot distinguish 0.47 from 0.56, and 10 should stop asking it to.** 10 says the golden set grows if the interval at 5 responses per point type is too wide to separate the GradeOpt-reported 0.47 from the CARO-reported 0.56. It is. Using Cohen's large-sample form as published, `SD(kappa) = sqrt(Po(1 - Po) / (1 - Pe)^2)` with `SE = SD / sqrt(N)` and a width of `2 x z x SE` (https://www.ncss.com/wp-content/themes/ncss/pdf/Procedures/PASS/Confidence_Intervals_for_Kappa.pdf [verified]), taking the most favourable case of balanced marginals, `Pe = 0.50`, with `Po = 0.78` which is exactly the observed agreement yielding kappa 0.56: `SD = sqrt(0.78 x 0.22 / 0.25) = 0.8285`. At the aggregate `N = 150`, `SE = 0.06765` and the 95 percent interval is `[0.427, 0.693]`, width 0.265. It contains 0.47 comfortably. **The 0.09 gap is 1.33 standard errors, so the standard error is about three quarters of the gap**, which is the ratio the right way round.

To exclude 0.47 the half width must be below 0.09, so `N > (1.96 x 0.8285 / 0.09)^2 = 325.5`, meaning **326 point decisions**. As responses on 30 point types that is 11 each, giving 330. As 5 responses each it needs **66 point types**, because 5 by 65 is 325 and fails the threshold by one. Comparing two kappas you estimated yourself needs `sqrt(2)` times the standard error and therefore **652 decisions an arm**. The implementation was validated against the published worked example on the same page, kappa 0.6 with `Po = 0.80` and `Pe = 0.50` giving `SD = 0.800` and `N = 984` for a width of 0.100, and it reproduces both.

At `N = 5` per point type the interval runs off both ends of the scale, so per-point-type kappa is not merely wide, it is the wrong instrument. **Decision: per-point-type kappa leaves the P3 gate and is replaced with per-point-type exact match reported with its count. Aggregate kappa is reported with its interval and is never gated against a literature value at this N.** The measurement that would overturn this: an aggregate kappa measured at 326 decisions or more, which is where the interval narrows enough for a literature comparison to mean anything. Growing 5 by 30 to 11 by 30 is `11 x 30 x 3 = 990` calls, **$14.26 a run, $7.78 more than today**, and the binding cost is the operator authoring 180 more responses, not the tokens.

**One eval the plan does not have.** Golden set 3 photographs pages under good light, low light, blur, angle, crossed-out work and margin work. None carries text addressed to the model. Two pages with an instruction written on them convert OWASP's segregate-untrusted-content control from absent to present and cost about a cent a run.
## Safety

**Every path by which attacker-controlled text can reach a model prompt, and what stops it.**

In P1 today there are none, by construction rather than by luck. Both shipped templates take app-controlled fields only. `render_template` at `app/providers/base.py:97` substitutes only into the section below the `<!-- prompt-variables -->` marker, and `split_template` hands the section above it to the system block, so no field can ever reach the system prompt [verified, by reading both functions]. That property is load bearing and should be stated in 07 as a rule rather than left as an implementation detail.

Path A, student-written text. Typed micro-session answers never reach a model, because R10 grades them deterministically. Error notes and self-explanations are written to `attempts` and are read by no prompt builder today [measured: `grep -rn error_note app/feedback app/providers`, no match; `self_explanation` matches only the prompt `app/feedback/render.py` shows to the student, which reads nothing back]. The live path arrives in P3, when the grader template takes the student's confirmed transcription and the diagnostician template takes the observed work. What stops it then: nothing yet. Substitution is raw, `app/providers/base.py:113` is `return str(fields[match.group(1)])`, with no escaping, no delimiting and no length bound, and `record_error_note` explicitly declines a length limit. The moment the grader template gains a transcription field, a student's page text is spliced verbatim into a user message with nothing marking where it begins and ends.

Path B, photographed page contents, two model hops. The page reaches the transcriber, where an injected instruction can be typographic as well as textual, and the read-back reaches the grader as text. What stops it: the read-back is shown to the student for confirmation before any grading call uses it, images are content-sniffed, re-encoded and size-bounded, the quality gate runs first, and R10 confines the path to a handful of sessions. What does not: nothing screens the transcriber's output before it becomes the grader's input, and the confirmation step is an accuracy control that happens to help security. The student clicking confirm is the person the control defends.

Path C, the official corpus cache under `cache/text/`. This is a theoretical surface and not a real one, and the reason is worth stating so nobody re-litigates it. Nothing in the plan puts corpus text in a prompt: 04 establishes `cache/text/<doc>/page-NNN.txt` as one of two corpora for the duplicate gate, which is a MinHash and embedding comparison rather than a prompt; 07's per-role parameter list gives the generator registry fields only; and 04 says outright that the generator never sees official stem text and that `forbidden_text` is empty by construction rather than by filtering. Provenance is operator controlled through `tools/fetch_corpus.py` against fixed College Board paths. The realistic threat to `cache/text/` is not injection but integrity: a poisoned or OCR-garbled page shifts the duplicate gate's similarity scores and produces a false negative, letting a near-copy through, and 04 already states that asymmetry, "a false positive costs one regeneration and a false negative costs a copyright exposure". `cache/manifest.json` carries a sha256 of the fetched PDF and the extracted text files downstream of it are unverified. That is an integrity gap, closed with a digest, not an injection surface.

**The published guidance, and the one control this design cannot use.** Anthropic's guidance for indirect injection is to put untrusted content only in `tool_result` blocks, never in a system prompt or a plain user text block, because the model is trained to treat instructions inside tool results with skepticism; to state the nature and source of the content explicitly; to carry an untrusted-content policy in the system prompt saying that tool, document and search content is data and never overrides the system prompt or the user's request; to JSON-encode untrusted content so that escaping gives unambiguous delimiters and an attacker cannot close a quote or a tag to break out; to apply least privilege; to screen tool outputs with a small model using structured outputs before acting on them; and to red-team the agent with deliberately injected documents (https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks [verified]). OWASP LLM01:2025 adds that multimodal exploitation is a named risk, "malicious actors could exploit interactions between modalities, such as hiding instructions in accompanying images", and lists segregating and clearly denoting untrusted content and conducting adversarial testing among its seven controls (https://genai.owasp.org/llmrisk/llm01-prompt-injection/ [verified]).

The headline Anthropic mitigation is unavailable here. 07 and 09 both commit to no tool definitions ever being sent, and `app/providers/anthropic.py:113` enforces it, so the trained-skepticism channel cannot be used. That is the right trade and it is not reopened, but it means the compensating controls are not optional. **Three rules, adopted.** Untrusted fields are JSON-encoded into the user message rather than raw-substituted, so a quote cannot be closed. Every role whose template carries an untrusted field, meaning the grader, the diagnostician and the transcriber, carries an untrusted-content policy block in its cached system prefix, which is free because the prefix is cached anyway. And the transcriber's output is screened by a Haiku 4.5 classifier with a strict schema before it becomes the grader's input, which at $1 and $5 per MTok costs about $0.001 a page and about $0.20 over the whole cycle.

**What must never enter an audit detail or a log line.** 09's list is a key or any part of one including a masked prefix, the passphrase, a raw provider response body, and the student's response text, and it extends to any log line, error message, stack trace, exception payload, URL path or query string. The code is clean where it writes: `app/providers/guard.py:394` returns provider, model, role and cap; `app/providers/guard.py:314` records `type(unreadable).__name__` rather than `str(unreadable)`, which is the right call because a `ValueError` raised while parsing a provider response is the object most likely to carry body fragments. Three gaps are named in the budget section above and are repeated here as rules rather than as observations. The seam scrubs the exceptions it did not raise. The plaintext key is never a named local on a frame that can raise. `write_audit` rejects a detail whose values exceed a length bound or match a key shape, in code rather than in prose.
